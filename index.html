1. Technical Overview & Concept

The system architecture 4.1 is designed using a multi-layer structure composed of the user layer, mobile application layer, cloud layer, and database layer. This architecture ensures smooth communication, efficient processing, and reliable data management across the entire system. It establishes the goal of improving laundry service efficiency through a mobile, map-based solution that enhances booking, delivery scheduling, and route optimization.

2. Architectural Layer Decomposition

  • User Layer: At the user layer, the system is accessed by customers, riders, and laundry shop owners. Customers place laundry pickup and delivery requests, riders manage delivery tasks and follow optimized routes, while administrators oversee and manage the overall system operations.
  • Mobile Application Layer: The mobile application layer, developed using React Native, serves as the main interface of the system. It allows users to interact with key features such as booking services, viewing map locations, tracking laundry status, receiving notifications, and communicating through chat. This layer ensures a responsive and user-friendly experience on mobile devices.
  • Cloud Layer: Powered by Laravel 11+ (PHP 8.3+) hosted on Render, the cloud layer provides online hosting and real-time connectivity. It enables the system to support multiple users simultaneously, ensures data synchronization, and allows real-time updates for tracking, notifications, and service status. This layer also improves system scalability and availability.
  • Database & External Services Layer: The database layer, powered by PostgreSQL 16 (hosted on Supabase), is responsible for storing and managing all system data, including user profiles, laundry orders, delivery schedules, route information, and transaction history. It ensures data integrity, consistency, and fast retrieval of information needed by the system. Mapping and route recommendations are handled using Google Maps Platform API and Leaflet.js, while native push notifications are powered by Firebase Cloud Messaging (FCM).

3. Operational Flow & Inter-Tier Communication

User actions on the React Native mobile application trigger API calls to the Laravel backend. The server processes request logic, verifies permissions, communicates with PostgreSQL through Eloquent ORM, and interacts with third-party mapping services for route recommendations. Notifications and live status updates are dispatched back to the mobile devices in real time, keeping all stakeholders coordinated.

4. Overall Summary & System Evaluation

Overall, these interconnected layers work together to provide a reliable, efficient, and real-time laundry pickup and delivery system that supports and improves service delivery for both users and the centralized laundry shop. The design directly supports the evaluation criteria under ISO/IEC 25010:2023, namely Functional Suitability, Interaction Capability, and Performance Efficiency.

1. Technical Overview & Purpose

A Data Flow Diagram (DFD) is a graphical representation that illustrates how data moves within a system process. It uses standardized symbols and notations to show data sources, processes, data storage, and outputs. The DFD helps visualize information flows between users, the mobile application, the backend system, and the database, providing a clear understanding of system operations and data interactions.

Shown in Figure 4.2, the Level 0 Data Flow Diagram (DFD) presents the context-level view of the system. In this diagram, the system is positioned at the center, representing the main process. External entities such as the Admin, Owner, Rider, and Customer interact with the system, and these interactions are illustrated through arrows that indicate the flow of data between each entity and the system.

2. External Entities & Data Interactions

  • Customer: Inputs registration/login credentials, service requests (service selection, preferred schedule, and detergent preferences), and reviews & feedback. In return, the customer receives map location coordinates, real-time laundry status updates, delivery/pickup service coordination, and order receipts.
  • Owner: Inputs login and sign-up details, services and pricing configurations, and laundry processing status updates, while receiving customer booking notifications and delivery assignment updates from the system.
  • Rider: Transmits rider login authentication, real-time map location updates, and delivery status changes, while receiving assigned pickup and delivery details, customer location information, and navigation directions.
  • Admin: Interacts with the system through admin console access, logging in to monitor overall system operations, verify transactions, manage user and shop accounts, and review system reports.

3. Overall Summary & System Scope

Overall, this diagram provides an overview of how information enters and exits the system, helping to clearly understand its overall functionality and scope. By centralizing all data exchanges through the core application, the system ensures seamless coordination among customers, laundry shops, and delivery personnel.

1. Technical Overview & Purpose

Figure 4.3 presents the Level 1 Data Flow Diagram (DFD). This diagram provides a more detailed representation of the system compared to the Level 0 diagram. While the Level 0 DFD illustrates the system as a single process, the Level 1 DFD breaks it down into smaller sub-processes to clearly show how data flows and how internal operations are carried out within the application.

2. Sub-Processes & Entity Operations

The diagram identifies the external entities—Admin, Owner, Rider, and Customer—and the specific actions they perform across eight core functional sub-processes:

  • 1.0 Login: Handles secure authentication, credential checking, and role verification for Customers, Shop Owners, Riders, and Admins.
  • 2.0 Service Request Management: Manages laundry booking requests, service type selections, detergent preferences, and order confirmations.
  • 3.0 Delivery Schedules: Coordinates pickup and delivery timings, organizes rider assignments, and manages delivery windows.
  • 4.0 Map Location: Processes geographic coordinates, landmark identification, and route visualization for customers and delivery riders.
  • 5.0 Laundry Status: Tracks and updates the live operational status of laundry orders from pickup through processing (wash, dry, fold) to final delivery.
  • 6.0 Chat Communication: Facilitates direct communication and messaging between customers, riders, and laundry shop owners to coordinate orders and resolve inquiries.
  • 7.0 Reviews & Feedback: Collects customer ratings and feedback regarding the service performance of the laundry shop and delivery riders.
  • 8.0 Account Management: Oversees user accounts, administrative CRUD operations, shop approvals, and platform governance.

3. Overall Summary & Functional Modularity

Overall, this detailed view helps in understanding how data is processed and how each component contributes to the overall functionality of the system. Isolating data transformations into structured sub-processes ensures high modularity, transactional consistency, and dependable operational coordination across the platform.

1. Technical Overview & Purpose

A Use Case Diagram is a high-level behavioral diagram and a fundamental component of the Unified Modeling Language (UML). It visually represents the interactions between users (actors), the system, and the use cases (functions) that users aim to accomplish. It outlines the system’s functionalities and illustrates how different users interact with the system to achieve specific objectives.

In this context, the use case diagram represents the interactions between the system and its primary users, namely the Customer, Rider, Admin, and Owner. The oval shapes (use cases) depict the actions that users can perform. The lines connecting actors to use cases, known as associations, indicate the interactions between users and the system functions.

2. Primary Actor Capabilities

  • Customer: Can perform functions including Register Account, Login, Request Pickup, Track Status, Feedback & Rate, View History, and Pay on Delivery.
  • Shop Owner: Can execute functionalities such as Login, Manage Services/Pricing, Manage Customer, Monitor Orders, and Track Rider.
  • Rider: Can manage delivery tasks including View Pickups, Navigate, Confirm Pickup, Contact Customer, and Deliver.
  • Administrator: Has additional privileges such as Create Shop Owner Account, Manage Users, and View System Reports to oversee overall system performance.

3. Stereotype Relationships (<<include>> and <<extend>>)

The diagram defines clear operational relationships between use cases:

  • <<include>> Relationships: The “include” relationship shows mandatory processes that are reused across different functions. For instance, customer and owner login include Verify Password; requesting a pickup includes Verify Address, Select Services, and Schedule; and delivering includes Update Laundry Status and Collect COD.
  • <<extend>> Relationships: The “extend” relationship represents optional or conditional functionalities. For example, login is extended by Display Error upon invalid input; requesting a pickup is extended by Cancel Pickup Request; and tracking status is extended by Receive Notification when order updates occur.

4. Overall Summary & Functional Integration

As shown in the figure, the system highlights key features such as service request management, delivery scheduling, map-based location tracking, route recommendation, laundry status monitoring, notifications, chat communication, and feedback. Overall, the use case diagram provides a clear visualization of how each user interacts with the system and how functionalities are integrated to support efficient laundry pickup and delivery services.

1. Technical Overview & Purpose

Figure 4.10 illustrates the landmark-based location and geocoding fallback mechanism of the application. In local communities such as Bulan, Sorsogon, customers often rely on nearby landmarks rather than complete street addresses. To improve location accuracy and usability, the application incorporates a landmark-based location feature and hierarchical fallback structure, allowing users to specify nearby recognizable places when setting pickup and delivery points.

2. Hierarchical Resolution Tiers

The algorithm processes customer delivery locations through five systematic tiers to ensure that every address resolves to valid spatial coordinates:

  • Tier 1: Hardware Device GPS Validation: Checks whether exact device GPS coordinates (latitude and longitude) are available from the mobile device and within the geographic boundaries of Bulan, Sorsogon.
  • Tier 2: Bulan Landmark Lookup: Matches user inputs against a curated dictionary of recognizable Bulan landmarks (such as SSU Bulan Campus, Bulan Public Market, Bulan Pier, Freedom Park, and Parish Church) to pinpoint the exact location.
  • Tier 3: Barangay Centroid Lookup: When specific landmarks are absent, matches the selected barangay against verified geographic coordinates across all sixty-three (63) barangays of Bulan.
  • Tier 4: Heuristic Text Keyword Scanning: Analyzes raw address strings for identifying keywords (such as purok, sitio, or street names) to associate the location with the closest recognized neighborhood.
  • Tier 5: Town Center Reference Offset: Serves as the final deterministic fallback based on the Bulan Municipal Center, applying an offset seed to prevent overlapping pins and guarantee valid routing.

Figure 4.13 illustrates the sequence of actions and decision-making processes for user authentication and password recovery. As established in the system's security specifications, secure user identification enhances account security, ensures user authenticity, and protects the platform against unauthorized access or misuse.

2. Verification Workflow & Credential Recovery

  • Password Reset Request: A user who forgets their password inputs their registered email address. The application transmits the request to the Laravel authentication API.
  • Cooldown & Rate-Limit Check: The system verifies if the request complies with rate-limiting rules (60-second cooldown). If valid, a secure 6-digit One-Time Password (OTP) is generated, hashed, and stored with an expiration window (10 minutes) in the database.
  • Code Dispatch: The OTP is sent to the user's email address via the mail service. The mobile application initiates a countdown timer and prompts for code entry.
  • Code Verification: The user enters the received OTP. The system validates the code against the database record. If valid, the user is authorized to proceed to password entry.
  • Password Update: The user submits a new secure password. The system verifies password requirements, updates the encrypted password in PostgreSQL, and invalidates the OTP token to complete the process.

3. Decision Points & Error Handling

Decision points are integrated throughout the flow to handle rate limit violations, invalid email inputs, incorrect or expired OTP entries, and password complexity validation. Clear error feedback and prompts guide users through each step, ensuring system reliability and account safety.
